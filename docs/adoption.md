# Adopting an existing model into the contract gates

> Repo path: `docs/adoption.md`
> The bottom-up path (D-35): you already have a hand-written dbt model, and
> you want the contract gates to enforce it. The describe stance drafts the
> contract from the table's own profile; deterministic tools measure the
> grain and finish the enforcement wiring; the same three gates that judge
> every contract judge yours. The gates never cared who wrote the model
> (D-08): this page is the path that makes an existing model their equal.

The scan drives the whole flow. `make scan` derives a review queue from the
model tree, `contracts/`, `profiles/`, the configuration, and the read-only
warehouse, and writes `plan.md` plus `plan.json` to the gitignored
`proposals/` outbox. Nothing is stored: re-run after each step and the
states flip. Every queue item names its exact next command. The scan,
`verify-grain`, and `enforce-properties` are deterministic code, never
agents (D-10 as amended); the only model call in this flow is the one
`make propose-describe` makes, and a human approves everything.

## The states

`adopt` (relation and profile present, no contract), `amend` (contract
present, evidence disagrees), `unenforced` (contract agrees, enforcement
keys missing), `contract_ahead` (the contract declares columns the relation
lacks; the fix is a model change, never a weaker contract, rule 6),
`needs_profile`, `needs_build`, and `in_sync`. Skips are jurisdictional:
engine-emitted gold under the ownership manifest is regenerated by PR,
never adopted (D-09); a gold model outside the manifest is reported and
never adopted, because gold stays engine-owned and a typed surface the
engine does not emit is never proposed (rule 12, D-35); views are
uncontracted until re-materialized as tables (rule 7); a model folder
outside bronze, silver, and gold is not classified.

## The checklist

For an existing hand-written silver model with no contract:

1. Materialize as `table` or `incremental`; views are uncontracted
   (rule 7). Build it:
   `uv run dbt build --project-dir transform --profiles-dir transform --target local --select <model>`.
2. `make scan`. The model reads `needs_profile`. Add the target to
   `config/default.yaml` under `profiling.targets`, then `make profile`.
   Re-scan: `adopt`.
3. `make propose-describe TABLE=<model>`. One structured call drafts the
   contract from the table's own profile artifact: every column with the
   exact type the engine produced, `required` from measured null rates, a
   proposed grain, and quality rules from a closed list. The draft, the
   proposal object, and the record land in the outbox; nothing under
   `contracts/` moves. Review the draft in your editor; it is yours to
   edit (D-24).
4. `make verify-grain TABLE=<model> KEYS=<a,b>`. The proposed grain is a
   judgment until the warehouse measures it (F-10). Expect 0 duplicate
   rows over the declared keys before you approve.
5. Copy the reviewed draft to `contracts/<model>.odcs.yaml` on a branch and
   open the contract-only PR with the D-08 version discipline. The three
   gates run; merge is approval. Re-scan: `unenforced`.
6. On a model branch:
   `uv run datacontract dbt sync contracts/<model>.odcs.yaml --project-dir transform --target local`
   CREATES the dbt properties file with the contract's exact types (F-27).
   Then `make enforce-properties TABLE=<model>` adds the only two keys sync
   omits: `contract.enforced: true` and `not_null` constraints on the
   contract's required columns (D-16 Amendment J). Review the diff; the
   file stays human-owned (rule 11); delete any `accepted_values: [0]`
   test on sight (F-05). Gates run; model PR; merge. Re-scan: `in_sync`.
7. From here the gates hold the model: a dropped column or a drifted type
   fails the build with a named mismatch, exactly as it does for every
   contracted model.

Steps 1, 2, 5, and 6 are existing practice; steps 3 and 4 are the
adoption capability. Why the profile and not the SQL: engines widen
aggregate types (a sum over INTEGER lands HUGEINT; a price extension
lands DECIMAL(38,2)), so a contract authored from the SQL text is wrong
where it matters and a contract authored from the profile is exact.

## Keeping it current

When the model changes shape, the scan reads `amend` and names the
disagreement. The amend stance proposes the declared change set over the
committed contract; until it lands, amend items report their next command
and wait. An amendment never weakens a contract without the explicit
relaxation flag and a major version bump (D-35, rule 6), and required
additions enter optional and tighten after the model lands (F-28).

## Walking the queue in batch

`make propose-queue MAX=<n>` walks the queue's `adopt` and `amend` items
in plan order, one structured call per item, and stops at the explicit
cap or the first fail-closed exit. Adopt items run the describe stance.
Amend items run only when the batch carries your `INTENT="..."`,
recorded verbatim in every proposal record; without it they are listed
with their exact per-item command and never invoked. A failed item stops
the batch and is never re-invoked unattended (D-10 as amended): review
the record, fix the cause, re-run the item yourself. The driver prints
tokens and cost per call and in total. Review stays per draft, one
contract per PR; the queue is derived fresh on every walk and nothing is
stored.

## Scope

The silver plane and the committed sample are the demonstrated scope
(D-35). Models whose columns the profiler cannot serialize (STRUCT, LIST,
BLOB) are out of scope for describe. Foreign gold is reported, never
adopted. Uniqueness stays in generated tests and the contract's
error-severity grain rule, never in trusted constraints (rule 5).
